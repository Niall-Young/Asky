## 已确认的耗时来源

1. **工具链扩张且串行执行。** `NativeRuntime.run` 按顺序等待每个工具，再发下一轮模型请求。京都那轮 13 次工具调用累计记录 39 个来源 attempt，其中 5 个因冷却跳过、34 个实际尝试。attempt 是服务或页面提取尝试，不是 HTTP 请求数量；一次 MCP 调用还可能包含初始化等网络交互。
2. **取图会遍历来源。** `WebReadPageTool.read` 在 `includeImages:true` 且正文没有图片时继续查询其他服务，最后才尝试直接提取页面图片元数据。京都多次出现 Parallel / Exa 已返回正文但图片为零，然后继续 Keenable 或 page_metadata 的情况。
3. **限流、超时和额外搜索。** 京都记录包含 Parallel 免费额度限流、Keenable 请求超时、Exa `CRAWL_NOT_FOUND`；最后一个页面请求因三个服务都在冷却而没有实际访问。明星记录包含页面提取失败和 Exa `CRAWL_LIVECRAWL_TIMEOUT`。部分搜索因未覆盖“照片”“人像”或中文拆词而查询备用来源；这些是匹配启发式的额外开销，不全是网络故障重试。
4. **正文只在完成后显示。** `AgentModel.handle` 暂存 textDelta，`finishTask` 才追加最终正文；`ChatResponseGroup.content` 隐藏运行中的 assistant 与工具过程，等待时只有三点气泡。这会使可感知等待覆盖整轮生成与工具时间，不证明模型首字同样慢。该行为在本次配图改动之前已存在，不能单独解释今天的增量。

## 缓存与上下文

- 网页缓存是 600 秒、最多 32 项/2 MiB 的内存缓存，相同键复用。京都与 17:58 明星样本中有缓存标记的返回均为 `cached:false`；未命中不等于缓存损坏。新 URL、不同搜索词、参数变化和重启均可能不复用。本次没有清缓存依据。
- 每轮从 SQLite 组装最近 40 条记录和搜索匹配，历史正文预算 40,000 字节，不是无限追加全部聊天。最近快照记忆索引仅 552 字节；49.52 秒与 85.03 秒样本的初始历史输入小于 2.56 秒样本，没有证据将这次退化归因于历史持续膨胀。
- **当轮工具结果仍会膨胀。** 京都累计工具结果为 193,089 UTF-8 字节，最终快照 228,249 字节；这些结果随工具循环重新发送。当前 180,000 字节压缩必须找到第二个 user 消息边界，而 App 每轮创建新 session，整个工具循环只有一个 user 消息，因此该样本不会触发压缩。需要单独控制当轮结果预算。
- 服务端 prompt cache 命中情况未知：当前 decoder 忽略 usage，未保存 cache hit/miss token 指标。系统提示前部含精确当前时间，但本次未验证其对服务端缓存的实际影响。
- 记忆提炼在完成后异步启动，不是这次发送前必须等待的步骤。可能与后续请求重叠，但现有记录不足以归因。

## 建议处理顺序（尚未实施）

1. 缩短找图路径：已有正文时尽早提取页面图片，减少为同一页面依次调用多个完整正文服务；对可选配图设总时间/尝试预算，避免为补齐图片拖住整个回答。
2. 对独立只读工具做有限并发，继续保持写操作的权限、顺序与取消边界；校准中文搜索匹配，减少缺少通用修饰词导致的备用查询。
3. 限制当轮工具返回总量，保留回答所需片段和来源；补齐无第二 user 边界时的上下文预算处理。
4. 记录请求开始、首字、每次工具耗时、总耗时及 usage/cache 指标，再做固定问题对照。是否改变整轮完成后显示的交互应单独决定；恢复流式展示只改善等待感，不能代替缩短工具链。
